# 무신사 iOS 앱 주문 플로우 테스트 계획서

**작성일** 2026-10-25 · **작성자** 이강혁 · **대상** 무신사 iOS 앱(App Store 배포 버전) · **문서 버전** v1.0

> 개인 QA 포트폴리오용 문서입니다. 무신사가 공개한 정책(고객센터 FAQ, 이용 안내)에서 요구사항을 역도출해 **테스트 계획과 케이스 설계까지**를 산출물로 합니다. 실행은 범위에 포함하지 않으며, 5장 실행 계획은 수행 시 따를 절차·통제 규칙을 설계 관점에서 기술한 것입니다. 무신사와는 무관합니다.

## 1. 개요

### 1.1 목적

- 장바구니 → 주문서(쿠폰·적립금·배송지·결제수단) → 결제 → 주문 취소에 이르는 주문 플로우가 공개 정책(REQ-01~15)과 일치하는지 검증
- 결제 금액 정합성(상품 금액 − 할인 − 적립금 + 배송비)과 결제 중단·취소 시 혜택(쿠폰·적립금) 복구를 중점 확인
- 공개 정책만으로 확정할 수 없는 동작을 질의사항(Q01~Q12)으로 분리해 실제 동작을 기록
- 모바일 앱 특화 관점(생명주기·네트워크·인터럽트·딥링크·접근성)을 체크리스트로 체계화해 케이스에 연결

### 1.2 배경

- 무신사 앱의 주문 플로우는 등급 할인, 상품 단위 쿠폰, 적립금(7%·10원 단위·5,000원 이상 보유), 선할인, 브랜드별 배송비, 결제수단별 즉시 할인·한도가 한 화면(주문서)에서 동시에 작용함
- 금액 계산 규칙이 여러 정책의 조합으로 결정되므로, 각 정책의 경계값과 조합을 설계 기법으로 체계화할 필요가 있음
- 요구사항은 별도 명세가 없어 공개 정책에서 역도출했고, 정책이 침묵하는 항목은 질의사항으로 관리함

### 1.4 가정 및 제약

- 산출물 범위: 테스트 계획서와 테스트 케이스(설계). 수행·결함 리포트는 범위 외이며, 케이스 파일의 결과·결함 시트는 수행 시 사용할 양식으로 제공
- 기기: iPhone 1종(iOS 26.5)을 기준 환경으로 하고 iOS·앱 버전을 결과에 기록. 두 번째 기기·버전은 확보 시 호환성 TC에 반영
- 계정: 개인 계정(M1)을 메인으로 가정. 등급·적립금·쿠폰 보유 조건은 '테스트 데이터' 시트에 정리하고, 충족 불가 조건의 TC는 Blocked로 사유 기록
- 실결제: 소액 상품 1~2건만 결제하고 결제완료 상태에서 즉시 취소. 환불은 결제수단별 소요 기간(카드 3~7영업일)을 따르며, 실결제 TC는 한 주문에 묶어 수행
- 재고·프로모션은 통제 불가. 품절·세일 종료 유도가 필요한 TC는 보조 계정(M4)과 타이밍으로 재현하고, 재현 불가 시 Blocked
- 정책은 변경될 수 있으므로 조회일(2026-10-25)을 명시. 수행 시점에 정책이 바뀌면 요구사항을 갱신하고 TC 변경 이력을 비고에 남김
- 정책 미정 항목은 2.2 질의사항으로 관리하고, 회신(확인) 전에는 '현재 동작 기록 후 판정' 원칙 적용

## 3. 테스트 전략

### 3.1 테스트 중점

- **금액 정합성**: 주문서에 표시되는 최종 결제 금액이 각 할인·적립금·배송비 항목의 합산과 1원 단위까지 일치해야 함. 정책 조합(등급 할인 × 쿠폰 × 적립금 × 배송비)과 각 한도의 경계값을 우선 설계
- **결제 중단·취소 복구**: PG·Apple Pay 이탈, 강제 종료, 가상계좌 미입금, 즉시 취소 후 쿠폰·적립금이 정확히 반환되는지. 돈과 혜택이 사라지는 결함은 영향이 가장 크므로 상태 전이를 주 설계 기법으로 사용
- **품절·가격 변동**: 장바구니 담기 이후 상태 변화가 주문서와 결제에 반영되는 시점
- **모바일 특화**: 앱 생명주기·네트워크·인터럽트 상황에서 주문서 상태와 중복 주문 방지

### 3.3 설계 기법

- **결정 테이블**: 적립금 사용 가능 판정(보유 금액 × 상품 허용 × 접속 경로 × 입력값) → PNT 그룹 도출(3.4)
- **경계값 분석**: 정책에 숫자가 명시된 항목은 기준 −10원 / 기준 / +10원(또는 ±1 단위)으로 3점 설계. 7% 한도는 기준 금액 정의(Q03·Q07)에 따라 재계산
- **상태 전이**: 주문·결제 상태 전이표(3.5)에서 모든 단일 전이와 중단 전이(이탈·강제 종료·인터럽트)를 TC로 도출
- **동등 분할**: 결제수단을 무신사머니 / 무신사페이 / 일반 결제(카드·간편결제·가상계좌·휴대폰)로 분할하고 각 분할에서 대표 수단 선택
- **오류 추정**: 결제 버튼 더블탭, 두 기기 동시 쿠폰 사용, 세일 종료 직후 결제, 만료 직후 쿠폰, 적립금 적용 후 쿠폰 변경에 따른 한도 재계산

## 5. 실행 계획

### 5.1 수행 순서

| 차수 | 대상 | 내용 | 비고 |
|---|---|---|---|
| 1차 | 비결제 TC 78건 | 결제 승인 전까지의 모든 TC. 장바구니 → 주문서 → 쿠폰/적립금 → 배송 → 결제수단 → PG 진입·이탈 순으로 수행 | P1 우선, 질의 항목은 현재 동작 기록 |
| 2차 | 실결제 TC 9건 | 소액 상품 1건을 쿠폰·적립금 적용으로 결제 → 더블탭(PAY-009) → 즉시 취소(CNL-001) → 쿠폰·적립금 반환(CNL-002/003) → 알림 확인(MOB-010)을 한 주문으로 연계. 부분 취소(CNL-004)는 2개 상품 주문 1건 별도 | 총 실결제 2~3건, 모두 결제완료 상태에서 즉시 취소 |

| 재검증 | Fail TC | 결함 수정 전제가 없으므로(외부 서비스) 재현율 확인 목적의 재수행 3회 | 재현율은 결함 리포트에 기록 |

### 5.2 실결제 통제 규칙

- 실결제는 1만 원 이하 상품(P9)으로 제한하고, 결제 직후 결제완료 상태에서 즉시 취소한다
- 가상계좌 주문은 입금하지 않고 48시간 자동 취소를 관찰한다(쿠폰·적립금 반환 확인 목적)
- 재고 경합·동시 사용 TC에서 실수로 결제된 주문은 즉시 취소하고 비고에 기록한다
- 무신사머니 자동 충전은 충전 실행 전 단계(안내 확인)에서 중단한다

|---|---|---|

| P2 | 정책 명시 항목의 경계·조합, 중단·복구 경로, 주요 모바일 상황 | 37 |
| P3 | 표기·UX·접근성, 발생 빈도가 낮은 조건 | 23 |

### 5.4 결과 판정

- **Pass / Fail / Blocked / N/A**를 케이스 시트의 결과 열에 기록. Blocked는 사전 조건 미충족(계정 등급, 재고, 프로모션 부재), N/A는 수행 시점에 기능이 존재하지 않는 경우
- 질의(Qn) 연결 TC는 실측·메모 열에 현재 동작을 먼저 기록하고, 정책·FAQ·앱 내 안내로 근거가 확인되면 그 기준으로 판정한다. 근거가 없으면 '현재 동작 기록'으로 두고 Fail 처리하지 않는다
- 결함은 '결함 리포트' 시트에 등록하고 TC의 결함 ID 열에 연결한다. 모든 Fail은 스크린샷 또는 화면 기록을 첨부한다

## 8. 자동화 전략

본 설계의 90건을 그대로 수동 회귀로 돌리면 1회 수행에 2~3일이 든다. 어떤 케이스를 어느 계층에서 자동화할지 정해 두면 회귀 비용이 줄고, 수동으로 남길 영역이 명확해진다. 케이스 시트의 '자동화 구분' 열과 요약 시트의 구분별 집계가 이 장의 근거다.

### 8.1 선정 기준

- **결정성**: 입력 → 출력이 정책으로 확정되는 케이스(금액 계산, 한도, 반환)는 자동화 1순위. 질의(Qn) 연결 케이스는 기대값이 확정된 뒤 자동화에 편입
- **반복 빈도**: 프로모션·쿠폰 정책이 바뀔 때마다 재검증해야 하는 금액 규칙은 회귀 가치가 높다
- **환경 통제 가능성**: 재고·시간·PG 응답을 테스트 환경에서 통제할 수 있어야 안정적이다. 통제 불가 항목은 수동으로 남긴다
- **계층 선택**: 같은 규칙이면 가장 낮은 계층(API)에서 검증한다. UI는 화면 전이·표시·사용자 흐름만 맡는다

### 8.3 API 계층 설계

주문서는 '입력 조합 → 금액 항목'을 돌려주는 계산 함수로 볼 수 있다. 장바구니 구성·쿠폰·적립금·배송지·결제수단을 입력으로 주면 상품 금액·등급 할인·쿠폰 할인·적립금·배송비·최종 결제 금액이 나온다. 이 계산을 **주문서 조회(견적) API** 한 번으로 검증하면 UI 없이 경계값·결정 테이블 전체를 돌릴 수 있다.

- **데이터 주도**: 경계값 3점·결정 테이블 행을 `parametrize` 케이스로 옮긴다. 케이스 ID를 TC ID와 1:1로 매핑해 결과를 케이스 시트에 역반영한다
- **정합성 공통 검증**: 모든 금액 케이스에 `상품 금액 − 등급 할인 − 쿠폰 할인 − 적립금 + 배송비 == 최종 결제 금액` 불변식을 공통 assertion으로 건다(TC-ORD-002의 자동화 형태)
- **상태 전이**: 주문 생성 → 모의 PG 승인 → 취소 → 쿠폰함·적립금 조회를 한 테스트에서 연결하고, 각 단계에서 쿠폰 상태·적립금 잔액을 확인한다(CNL 그룹). 가상계좌 48시간·쿠폰 만료는 서버 시간을 주입하거나 만료 시각을 짧게 설정한 테스트 쿠폰으로 대체한다
- **동시성**: 같은 쿠폰·마지막 재고에 대해 두 요청을 동시에 보내 한쪽만 성공하는지 확인한다(CPN-009, SEC-006). `asyncio.gather`로 동시 호출
- **테스트 데이터 격리**: 전용 테스트 계정·상품·쿠폰을 시드로 만들고 각 테스트가 자기 데이터만 쓴다. 적립금 잔액처럼 상태가 남는 값은 테스트 시작 시 API로 초기화한다
- **PG 모의**: 승인·실패(한도 초과)·타임아웃 응답을 선택할 수 있는 모의 PG를 전제로 한다. 실제 PG는 자동화 범위에서 제외

예시 — TC-PNT-003(7% 한도 경계)과 TC-PNT-004(10원 단위)를 하나의 파라미터 테이블로:

```python
@pytest.mark.parametrize("tc_id, cart_total, point_input, expected_point", [
    ("TC-PNT-003-1", 100_000, 7_000, 7_000),   # 한도와 같음 → 적용
    ("TC-PNT-003-2", 100_000, 7_010, 7_000),   # 한도 초과 → 보정(또는 거부: Q03 확정 후 기대값 고정)
    ("TC-PNT-003-3", 100_000, 6_990, 6_990),   # 한도 미만 → 적용
    ("TC-PNT-004-1", 100_000, 1_005, 1_000),   # 10원 단위 절사
    ("TC-PNT-004-3", 100_000, 1_000, 1_000),
])
def test_point_limit(order_api, seeded_cart, tc_id, cart_total, point_input, expected_point):
    quote = order_api.quote(cart=seeded_cart(total=cart_total), point=point_input)
    assert quote.point_used == expected_point
    assert quote.total == quote.item_total - quote.grade_discount - quote.coupon_discount - quote.point_used + quote.shipping_fee
```

### 8.4 UI 계층 설계

- **범위**: 사용자 흐름이 끊기지 않는지 보는 E2E 스모크(장바구니 담기 → 주문서 → 쿠폰 1건 → 적립금 입력 → 결제수단 선택 → PG 진입 직전)와 화면 표시 검증. 금액 계산은 UI에서 재검증하지 않고 API 계층에 맡긴다
- **도구**: Appium 2 + XCUITest driver, pytest. 로케이터는 `accessibilityIdentifier`를 개발팀에 요청해 텍스트 의존을 없앤다(다국어·문구 변경에 강함)
- **구조**: Page Object(ProductPage, CartPage, CheckoutPage, PaymentPage) + 흐름 단위 헬퍼. 테스트는 '무엇을 확인하는가'만 남기고 조작은 페이지 객체에 둔다
- **모바일 상황 자동화**: 백그라운드 복귀는 `background_app(seconds)`로, 딥링크·유니버설 링크는 URL로 앱을 실행해 상품 상세 도달을 확인한다(MOB-001, MOB-006). 강제 종료는 `terminate_app` → `activate_app`으로 장바구니 유지를 확인한다(CART-009)
- **기기 매트릭스**: 실기기 1대(최신 iOS) + 시뮬레이터(직전 iOS, 소형·대형 화면)에서 같은 스모크를 돌린다(CMP-001/002). 레이아웃 깨짐은 스크린샷 비교로 보조
- **플래키 대책**: 명시적 대기만 사용(sleep 금지), 실패 시 1회 재시도 후 스크린샷·화면 녹화·앱 로그 첨부, 네트워크 의존 단계는 API로 사전 조건을 만든 뒤 UI는 확인만 한다

### 8.6 CI 운영

- **PR 단위**: API 계층 스위트 전체(수 분). 금액 규칙 회귀를 매 변경마다 보장
- **나이틀리**: UI 스모크를 macOS 러너에서 시뮬레이터 매트릭스로 실행. 실기기는 주 1회 또는 릴리스 전
- **리포트**: Allure로 TC ID별 결과·첨부를 모으고, 결과를 케이스 시트의 결과 열에 역반영하는 스크립트를 둔다(수동·자동 결과가 한 집계에 보이도록)
- **실패 분류**: 제품 결함 / 테스트 데이터 / 환경(PG 모의·네트워크) / 플래키를 태깅해 결함률과 자동화 신뢰도를 따로 본다

### 8.7 외부 포트폴리오로서의 제약

API 계층은 사내 테스트 환경·API 명세·모의 PG가 있어야 성립하므로 **설계안**이다. 외부에서 실제로 구현할 수 있는 것은 Appium UI 스모크(비결제 범위)뿐이며, 프로덕션 서비스에 자동화 트래픽을 보내는 것은 하지 않는다. 사내에 들어간다면 8.3의 데이터 주도 금액 테스트를 가장 먼저 구현한다 — 결함 영향이 가장 크고, 정책 변경 시 회귀가 가장 자주 필요한 영역이기 때문이다.
