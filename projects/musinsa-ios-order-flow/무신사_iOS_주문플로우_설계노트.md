# 무신사 iOS 앱 주문 플로우 테스트 — 설계 노트

**작성일** 2026-10-25 · **작성자** 이강혁

이 문서는 테스트 계획서와 케이스를 만들면서 내린 **설계 결정과 그 이유**를 기록한 것이다. 계획서가 "무엇을 어떻게 테스트하는가"라면, 이 문서는 "왜 그렇게 결정했는가"다. 각 항목은 결정 → 고려한 대안 → 선택 이유 → 결과 순으로 적었다.

---

## 1. 대상 선정: 왜 무신사, 왜 주문 플로우인가

**결정** 무신사 iOS 앱의 장바구니 → 주문서 → 결제 → 취소 흐름을 대상으로 한다.

**대안**
- 검색·필터·랭킹 같은 탐색 기능 — 화면이 많고 케이스를 늘리기 쉬움
- 회원가입·로그인 — 범용적이지만 정책이 단순함
- 주문 플로우 — 정책이 여러 개 겹치고, 돈이 걸림

**이유** 주문서 한 화면에서 등급 할인 × 상품 단위 쿠폰 × 적립금(5,000원 이상·7%·10원 단위) × 선할인 × 브랜드별 배송비 × 결제수단 즉시 할인·한도가 **동시에 계산**된다. 정책이 조합되는 지점은 결함 밀도가 높고, 틀리면 바로 환불·CS로 이어진다. 테스트 설계 역량(경계값·조합·상태 전이)을 보여주기에 가장 밀도 높은 영역이다.

**결과** 10개 대분류 90건 중 금액·쿠폰·적립금·배송비·결제수단 관련이 49건으로 절반 이상을 차지한다.

---

## 2. 요구사항이 없는 서비스에서 요구사항 기반 테스트를 하는 방법

**결정** 무신사 고객센터 FAQ·이용 안내에서 요구사항 15건을 **역도출**하고, 각 요구사항에 출처를 남긴다.

**대안**
- 앱을 조작해 보고 관찰한 동작을 요구사항으로 적기
- 요구사항 없이 탐색적 테스트 체크리스트만 작성하기
- 공개 정책에서 역도출하기

**이유** 구현을 보고 요구사항을 쓰면 **결함을 정상으로 오판**한다. 테스트의 독립성이 사라진다. 반면 FAQ는 회사가 고객에게 공개적으로 약속한 문장이므로 검증 기준으로 정당하다. "적립금은 5,000원 이상 보유 시 사용 가능", "결제 금액의 최대 7%, 10원 단위", "결제완료 상태 취소 시 쿠폰·적립금 반환"처럼 **숫자와 규칙이 박힌 문장만** 요구사항으로 채택했다. 출처가 없는 요구사항은 추측이므로 15건 전부 출처 열을 뒀다.

**결과** 요구사항 추적 매트릭스(계획서 2.1)와 요약 시트의 커버리지 집계가 가능해졌다. 요구사항 기반 TC 37건, 리스크 기반 26건, 추가 검증 27건으로 근거가 분리된다.

## 3. 정책이 침묵하는 항목: 질의사항으로 분리

**결정** 공개 정책만으로 기대결과를 확정할 수 없는 12건을 질의사항(Q01~Q12)으로 분리하고, 연결 TC의 기대결과에 "Qn 회신 후 확정"을 표기한다. 회신 전 처리 원칙은 "현재 동작 기록 후 판정".

**대안**
- 가장 그럴듯한 동작을 기대결과로 적기
- 해당 TC를 아예 만들지 않기

**이유** 배송비가 브랜드별인지, 7% 한도의 기준 금액이 쿠폰 적용 전인지 후인지, PG 화면에서 이탈하면 쿠폰이 즉시 반환되는지 — FAQ에 없다. 지어낸 기대결과로 Fail을 내면 결함이 아니라 테스터 의견이 된다. 실무에서 기획자에게 질의하는 자리에 "앱 관찰"을 넣은 것이며, 이 구조는 명세가 불완전한 어떤 프로젝트에도 그대로 쓸 수 있다.

**결과** 질의 연결 TC는 실측·메모 열에 현재 동작을 먼저 기록하고 근거가 생기면 판정한다(계획서 5.4). 질의 1건당 영향 TC 수가 요약 시트에 집계되어, 어떤 질의가 먼저 풀려야 하는지 우선순위가 보인다(Q03 8건, Q01·Q06 7건).

## 4. 설계 기법: 규칙의 형태에 기법을 맞추기

**결정** 기법을 나열하지 않고, 각 정책이 어떤 형태인지에 따라 기법을 매칭한다.

| 규칙의 형태 | 기법 | 적용한 곳 |
|---|---|---|
| 조건 여러 개가 AND로 결합되어 결과가 정해짐 | 결정 테이블 | 적립금 사용 가능 판정(보유 ≥ 5,000 × 상품 허용 × 바로 접속 × 한도·단위). 4조건 16조합을 5행으로 축약 |
| 숫자 기준이 명시됨 | 경계값 분석(3점) | 5,000원 / 7% / 10원 / 쿠폰 최소 주문·최대 할인 / 무료배송 조건 / 휴대폰 50만·무신사머니 200만 / 48시간 |
| 상태가 바뀌며 부수효과가 따름 | 상태 전이 | 주문서 → PG → 결제완료·이탈, 입금대기 → 자동취소, 결제완료 → 취소완료. 전이마다 "쿠폰·적립금이 어디로 가는가"가 검증 포인트 |
| 종류는 많지만 동작 원리가 같음 | 동등 분할 | 결제수단 9종을 무신사머니 / 무신사페이 / 일반 결제로 분할, 대표만 깊게 |
| 정책엔 없지만 경험상 자주 깨짐 | 오류 추정 | 결제 버튼 더블탭, 두 기기 동시 쿠폰 사용, 세일 종료 직후 결제, 만료 직전 쿠폰, 적립금 적용 후 쿠폰 변경 |

**이유** "경계값 분석을 사용했다"는 문장은 정보가 없다. 어떤 규칙에 왜 그 기법이 맞는지가 설계 역량이다. 오류 추정으로 나온 케이스는 요구사항 근거가 없으므로 설계 근거를 '리스크 기반'으로 따로 태깅해 요구사항 커버리지와 섞이지 않게 했다.

## 5. 경계값에서 특별히 고려한 것

### 5.1 기준 금액을 모를 때의 경계값

7% 한도의 기준 금액(상품 금액 / 쿠폰 적용 후 / 배송비 포함)을 정책이 말해주지 않는다. 기준이 다르면 7,000원이 다른 숫자가 된다.

**결정** 두 종류의 TC로 나눴다.
- **규칙을 검증하는 TC**(TC-PNT-003): 쿠폰을 적용하지 않은 상태로 상품 금액을 정확히 100,000원으로 맞춰 변수를 제거하고 7,000 / 7,010 / 6,990을 입력한다.
- **규칙을 알아내는 TC**(TC-CPN-006): 쿠폰 적용 전과 후의 최대 사용 가능 금액을 둘 다 기록해 기준 금액을 역산한다.

**이유** 모르는 변수가 있을 때 한 TC에 다 넣으면 실패 원인을 분리할 수 없다. 변수를 고정한 TC와 변수를 밝히는 TC를 분리해야 결과 해석이 가능하다.

### 5.2 정책 두 개가 충돌하는 지점

보유 적립금이 5,614원처럼 10원 단위가 아닐 때 [전액 사용]을 누르면, "최대한 많이 사용"과 "10원 단위만 사용"이 충돌한다(TC-PNT-005).

**이유** 결함은 정책 하나의 경계보다 **정책 두 개가 만나는 곳**에 숨는다. 5,614원이 그대로 적용되면 REQ-04 위반이고, 이런 케이스는 정책을 따로따로 읽어서는 나오지 않는다.

### 5.3 3점 설계의 ±단위

금액은 ±10원, 시간은 만료 직전·직후, 수량은 상한·상한+1로 통일했다. 적립금이 10원 단위이므로 ±1원은 의미가 없고, ±10원이 정책상 최소 단위다.

## 6. 우선순위와 실행 구분을 별도 축으로 둔 이유

**결정** P1~P3(중요도)와 별도로 실행 구분(비결제 / 실결제 / 장기)을 태깅한다.

**대안** 우선순위 하나로 관리하고 실결제 여부는 비고에 적기

**이유** 중요도와 비용은 다른 축이다. "결제 버튼 더블탭 시 주문 1건만 생성"(P1·실결제)과 "품절 상품 결제 차단"(P1·비결제)은 같은 날 수행할 수 없다. 두 축이 있어야 수행 순서 — 1차 비결제 전수 → 2차 실결제를 한 주문으로 묶기 → 3차 장기 — 가 **설계에서 자동으로 도출**된다. 실결제 통제 규칙(소액 1~2건, 즉시 취소, 가상계좌는 미입금 관찰)도 이 축이 있어야 적을 자리가 생긴다.

**결과** 비결제 78 / 실결제 9 / 장기 3. 요약 시트에 실행 구분별 집계가 있다.

## 7. 모바일 체크리스트를 TC와 분리한 이유

**결정** 앱 특화 관점 10개(생명주기·네트워크·인터럽트·진입 경로·OS 통합·권한·설치/업데이트·기기 매트릭스·접근성·동기화)를 체크리스트 시트로 두고 각 관점을 TC에 연결한다.

**이유** 모바일이 웹과 다른 건 기능이 아니라 **환경**이다. 백그라운드 복귀, 전화 수신, 네트워크 전환, 푸시 진입, 강제 종료. 이런 케이스를 기능 TC 사이에 섞으면 "왜 이 케이스가 있지?"가 보이지 않는다. 관점 목록에서 TC로 내려가는 구조여야 빠진 관점을 찾을 수 있고, 다음 프로젝트에서도 재사용할 수 있다.

**사례** TC-MOB-004(PG 화면에서 전화 수신 후 복귀)는 '인터럽트' 관점과 '결제 상태 전이'가 교차하는 케이스다. 두 축이 모두 있어야 나온다.

## 8. 자동화 계층: 금액 규칙은 UI에서 검증하지 않는다

**결정** 90건을 API 48 / UI 23 / 수동 19로 배치한다. 금액 계산·한도·반환은 API, 흐름·표시는 UI, OS 통합 영역은 수동.

**대안**
- 전부 UI(Appium) 자동화
- 수동 설계만 하고 자동화는 언급하지 않기

**이유** 주문서는 "장바구니 + 쿠폰 + 적립금 + 배송지 → 금액 항목"을 돌려주는 **계산 함수**다. 경계값 3점과 결정 테이블을 UI로 돌리면 케이스당 수십 초에 플래키가 붙지만, 견적 API 한 번이면 결정적이고 빠르다. 같은 규칙이면 가장 낮은 계층에서 검증한다는 원칙을 세웠다.

핵심 장치 두 가지:
- **TC ID를 자동화 케이스 ID로 그대로 사용**(parametrize). 설계 문서와 코드가 1:1이 되어 결과를 케이스 시트에 역반영할 수 있다.
- **불변식을 공통 assertion으로**: `상품 금액 − 등급 할인 − 쿠폰 할인 − 적립금 + 배송비 == 최종 결제 금액`. TC-ORD-002가 자동화에서는 케이스 하나가 아니라 모든 금액 케이스가 통과해야 하는 조건이 된다.

수동 19건은 "못 해서"가 아니라 "비용 대비 신뢰도가 낮아서"다. Apple Pay 시트, PG 웹뷰, 전화 인터럽트, iOS 네트워크 토글, 접근성 육안 판단은 자동화 로케이터가 불안정하거나 테스트 코드로 제어할 수 없다. 각 항목의 이유를 계획서 8.5에 표로 남겼다.

**제약** API 계층은 사내 테스트 환경·API 명세·모의 PG를 전제로 한 설계안이다. 외부에서 실제 구현 가능한 것은 Appium UI 스모크(비결제 범위)뿐이며, 프로덕션에 자동화 트래픽을 보내지 않는다.

## 9. 의도적으로 제외한 것

| 제외 항목 | 이유 |
|---|---|
| 트래픽 변조(프록시)로 금액 조작 검증 | 타사 프로덕션에 수행하면 안 되고, 포트폴리오에서는 역효과. 사내라면 보안 테스트 범위로 분리 |
| 교환·반품 | 취소보다 상태가 길고 실물이 오가야 함. 설계 가치 대비 비용이 큼 |
| 실결제 다건·테스트 실행 자체 | 설계 역량이 목적. 실결제는 비용·윤리 문제. 대신 "한다면 어떻게 통제하는가"(계획서 5.2)를 설계에 남김 |
| 무신사머니 충전·인출, 래플·USED·부티크 | 주문 플로우 밖의 별도 도메인 |
| 성능·부하 | 외부에서 수행 불가, 설계 목적과 무관 |

## 10. 한계와 사내 환경이라면 달라질 것

- **요구사항의 정확도**: FAQ는 고객 안내문이라 예외와 내부 규칙이 빠져 있다. 사내라면 기획 명세·정책 테이블을 기준으로 삼고 질의 12건 대부분이 명세로 해소된다.
- **테스트 데이터 통제**: 재고·세일 종료·만료 시각을 외부에서 통제할 수 없어 일부 TC가 Blocked 위험이 있다. 사내 테스트 환경이면 시드 데이터와 서버 시간 주입으로 해결된다.
- **실행과 결함**: 이 프로젝트는 설계까지다. 실행했다면 질의 12건의 확인 결과, 결함 리포트, 수행률·Pass율이 추가되고, 설계가 실제로 결함을 찾았는지로 평가받게 된다.
- **자동화 구현**: 8장의 API 데이터 주도 테스트를 가장 먼저 구현한다. 결함 영향이 가장 크고 정책 변경 시 회귀가 가장 자주 필요한 영역이기 때문이다.

## 11. 한 문장 요약과 예상 질문

### 11.1 한 문장으로

> 명세가 없는 실서비스에서 공개 정책으로 요구사항을 세우고, 모르는 것은 질의로 분리하고, 돈이 걸린 금액 계산을 결정 테이블·경계값·상태 전이로 90건 설계한 뒤, 그중 절반을 API 자동화 계층으로 내려보낸 테스트 설계안.

### 11.2 설계 하이라이트 3가지

1. **역도출 요구사항 + 질의 분리** — 출처 있는 요구사항 15건과 "현재 동작 기록 후 판정" 원칙의 질의 12건. 명세가 불완전한 어떤 프로젝트에도 재사용 가능한 구조
2. **규칙을 검증하는 TC와 규칙을 알아내는 TC의 분리** — 7% 한도의 기준 금액처럼 모르는 변수가 있을 때, 변수를 고정한 TC(PNT-003)와 변수를 밝히는 TC(CPN-006)를 나눠 결과 해석을 가능하게 함
3. **금액 규칙은 API 계층에서** — 주문서를 계산 함수로 보고 TC ID 1:1 데이터 주도 테스트와 불변식 assertion으로 설계. UI는 흐름·표시만

### 11.3 예상 질문과 답

| 질문 | 답 | 근거 위치 |
|---|---|---|
| 왜 무신사, 왜 주문 플로우인가? | 정책 5개가 한 화면에서 조합되는 곳이라 결함 밀도와 영향(환불·CS)이 가장 큼 | 노트 1장 |
| 요구사항을 지어낸 것 아닌가? | 15건 전부 FAQ·안내 페이지 출처 표기. 정책이 침묵하는 12건은 질의로 분리하고 Fail 처리하지 않음 | 노트 2·3장, 계획서 2.1·2.2 |
| 7%의 기준 금액을 모르는데 경계값을 어떻게 잡았나? | 쿠폰을 뺀 상태로 변수를 제거해 검증(PNT-003), 쿠폰 전/후 한도를 둘 다 기록해 기준을 역산(CPN-006) | 노트 5.1 |
| 경계값 외에 어떤 케이스가 결함을 잘 찾나? | 정책 두 개가 충돌하는 지점. 예: 보유 5,614원에서 [전액 사용] — "최대한 사용"과 "10원 단위"의 충돌(PNT-005) | 노트 5.2 |
| 우선순위 말고 실행 구분은 왜 있나? | 중요도와 비용은 다른 축. 이 축이 있어야 수행 순서(비결제 전수 → 실결제 한 주문 묶기 → 장기)가 자동 도출됨 | 노트 6장, 계획서 5.1 |
| 앱 테스트는 처음인데 무엇을 봤나? | 기능이 아니라 환경이 다름. 10개 관점(생명주기·네트워크·인터럽트·진입 경로·OS 통합·권한·업데이트·기기·접근성·동기화)을 체크리스트로 세우고 TC에 연결 | 노트 7장, 케이스 '모바일 체크리스트' 시트 |
| 자동화는 무엇부터 하나? | 8장의 API 데이터 주도 금액 테스트. 결함 영향 최대, 정책 변경 시 회귀 최빈 | 노트 8장, 계획서 8.3 |
| 왜 전부 UI 자동화하지 않았나? | 같은 규칙이면 가장 낮은 계층에서. 금액 계산을 UI로 돌리면 느리고 플래키함. 수동 19건은 OS 통합 영역이라 비용 대비 신뢰도가 낮음 | 계획서 8.2·8.5 |
| 실행은 왜 안 했나? | 설계 역량이 목적. 실결제는 비용·윤리 문제로 범위 외. 대신 "한다면 어떻게 통제하는가"를 설계에 남김 | 노트 9장, 계획서 5.2 |
| 사내에 들어가면 무엇이 달라지나? | 요구사항이 명세로 대체되어 질의 대부분이 해소, 테스트 데이터·시간·PG를 통제할 수 있어 Blocked 위험 제거, API 자동화 구현 가능 | 노트 10장 |
