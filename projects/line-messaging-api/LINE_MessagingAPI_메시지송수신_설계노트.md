# LINE Messaging API 메시지 송수신 테스트 — 설계 노트

**작성일** 2026-10-25 · **작성자** 이강혁

이 문서는 테스트 계획서와 케이스를 만들면서 내린 **설계 결정과 그 이유**를 기록한 것이다. 계획서가 "무엇을 어떻게 테스트하는가"라면, 이 문서는 "왜 그렇게 결정했는가"다. 각 항목은 결정 → 고려한 대안 → 선택 이유 → 결과 순으로 적었다.

---

## 1. 대상 선정: 왜 LINE, 왜 Messaging API, 왜 송수신인가

**결정** LINE Messaging API의 메시지 발송(reply·push·multicast·broadcast·narrowcast) → 웹훅 수신 → 서명 검증 → 재시도·재전송 흐름을 대상으로 한다.

**대안**
- LINE Login — OAuth 2.0/OIDC 표준 흐름. 인증·토큰 상태 전이는 좋지만 4번 프로젝트(SSO)와 관점이 겹침
- 리치 메뉴·오디언스 관리 — CRUD가 많아 케이스 수는 늘지만 품질 관점이 단조로움
- 메시지 송수신 — 플랫폼 API 품질 관점(계약·인증·멱등성·레이트리밋·웹훅)이 한 흐름에 전부 들어 있음

**이유** 송수신 흐름에는 "우리가 호출하는 API"와 "플랫폼이 우리를 호출하는 웹훅"이 한 쌍으로 들어 있다. 멱등성(리트라이 키), 비동기 상태(narrowcast), 페이지네이션(팔로워 ID), 레이트리밋(토큰 버킷), 웹훅 보안(HMAC 서명)과 신뢰성(재전송·중복·순서)이 모두 등장해, 플랫폼 API 테스트 설계 역량을 한 프로젝트로 보여주기에 가장 밀도가 높다. 1번 프로젝트(커머스 B2C 앱)와 축이 달라 포트폴리오 폭도 넓어진다.

**결과** 12개 대분류 102건 중 멱등성·웹훅(IDM·WHK·WHS) 27건, 계약·인증(AUTH·CMN) 18건, 메시지·발송(RPL·PSH·MLT·MSG) 37건으로 플랫폼 API 관점이 고르게 배치됐다.

## 2. 요구사항이 '있는' 서비스에서 요구사항을 역도출한 이유

**결정** 공개 API reference와 docs에서 요구사항 22건을 역도출하고 각 항목에 출처(레퍼런스 섹션·문서명)를 남긴다.

**대안**
- 레퍼런스 자체를 요구사항으로 삼고 TC를 엔드포인트별로 1:1 작성
- SDK 동작을 관찰해 요구사항으로 적기

**이유** 레퍼런스는 엔드포인트 단위로 쓰여 있어 "리트라이 키는 24시간 보관된다"(Retrying), "같은 키는 409"(Status codes), "push는 원 sentMessages를 돌려준다"(Retry responses)처럼 **한 규칙이 세 곳에 흩어져** 있다. 흩어진 문장을 규칙 단위로 모아야 결정 테이블·상태 전이를 만들 수 있다. 1번 프로젝트와 다른 점은 문서가 숫자·상태 코드를 명시해 요구사항 기반 TC 비중이 높다는 것(83/102)이며, 이는 설계 결함이 아니라 명세 품질의 차이다. 대신 문서에 없는 구현 함정(재직렬화 후 서명, 첫 요청 키 누락, 동기 처리 타임아웃)을 리스크 기반 16건으로 분리했다.

**결과** 요구사항 추적 매트릭스(계획서 2.1)에서 연결 TC 0인 요구사항이 없고(빌드 스크립트가 assert), 요약 시트에서 요구사항별 Pass/Fail이 집계된다.

## 3. 문서가 '비보장'이라고 쓴 항목: 질의가 아니라 관찰로 분리

**결정** 공개 문서만으로 확정 불가한 13건을 질의(Q01~Q13)로 분리하되, 문서가 명시적으로 "보장하지 않는다"고 쓴 2건(reply token 1분 경계 Q07, 재전송 횟수·간격 Q09)은 Pass/Fail 대신 **'관찰'**로 판정한다.

**대안**
- 1분 경계를 59/60/61초 경계값으로 Fail 판정
- 비보장 항목은 TC를 만들지 않기

**이유** LINE 문서는 "Use beyond one minute isn't guaranteed to work"와 "don't rely on the time limit"를 함께 적어 두었다. 61초에 400이 나와도 60초에 400이 나와도 결함이 아니다. 이런 항목을 Fail로 적으면 테스터 의견이 결함으로 둔갑한다. 반대로 TC를 만들지 않으면 "토큰을 즉시 써야 한다"는 설계 권고가 어디서 나왔는지 근거가 사라진다. 그래서 3회 측정 분포를 기록하는 관찰 항목(TC-RPL-003)으로 두고, 결론을 클라이언트 설계 규칙(수신 즉시 사용)으로 옮겼다.

**결과** 질의 1건당 영향 TC 수가 요약 시트에 집계된다(Q08·Q11 3건, Q03·Q04·Q09·Q10·Q12 2건). 질의 중 4건(Q01·Q02·Q04·Q11)은 자동화 assertion의 기대값을 확정하는 용도라 회신 즉시 코드에 반영된다.

## 4. 설계 기법: 규칙의 형태에 기법을 맞추기

**결정** 기법을 나열하지 않고, 각 규칙의 형태에 따라 기법을 매칭한다(계획서 3.3 표).

| 규칙의 형태 | 기법 | 적용한 곳 |
|---|---|---|
| 조건 AND 결합 → 응답 결정 | 결정 테이블 | 푸시 발송 결과(토큰 × 메시지 × 대상 존재 × 수신 가능), 리트라이 키 처리(지원 엔드포인트 × 키 × 수락 이력) |
| 숫자 한도 명시 | 경계값 3점 | 5개 메시지, 5000 UTF-16 유닛, 500 userId, 13 quick reply, 20 이모지, 30자 유닛명, limit 1000, 500자 URL, 15분·24시간·14일 |
| 시간에 따른 상태 변화 | 상태 전이 | 리트라이 키 요청 상태, 웹훅 전달·재전송 상태, narrowcast phase, 토큰 수명 |
| 동작이 같은 입력 집합 | 동등 분할 | 메시지 타입 6종, 토큰 4종, 대상 유형 3종, 429 두 종류, 재시도 가능/불가 상태 코드 |
| 독립 변수 조합이 많음 | 페어와이즈 | 엔드포인트 4 × 타입 6 × 알림 2 = 48 → 10조합 |
| 구현에서 자주 틀리는 지점 | 오류 추정 | 재직렬화 후 서명, 헤더 대소문자, 특수문자 본문, 같은 키·다른 본문, 첫 요청 키 누락, 동기 처리, 순서 역전 |

**이유** 면접에서 "경계값을 썼다"는 답보다 "7개 숫자 한도 중 시간 한도는 ±10초, 개수 한도는 ±1로 잡았고, 5000자는 글자가 아니라 UTF-16 코드 유닛이라 이모지 2500개를 경계로 뒀다"가 설득력 있다. 규칙 → 기법 매칭은 기법 선택 이유를 자동으로 설명한다.

**결과** 결정 테이블 2개, 상태 전이표 2개, 페어와이즈 표 1개가 `tc_data.py`에 데이터로 들어 있어 계획서가 자동 생성된다.

## 5. 경계값에서 특별히 고려한 것

### 5.1 '글자 수'가 아니라 코드 유닛

text 5000자 한도는 UTF-16 코드 유닛 기준이다. ASCII 5000자와 '🍎' 2500개(5000 유닛)가 같은 경계이고, 결합 이모지('👨‍👩‍👧', 8 유닛)는 625개가 경계다(TC-MSG-002). 한글은 1 유닛이라 5000자가 경계다. 글자 수로 경계를 잡으면 이모지가 섞인 실사용 텍스트에서 400을 예측하지 못한다. 반대로 action label은 grapheme cluster 기준이라(TC-MSG-006) 같은 '길이'라도 세는 단위가 다르다는 점을 TC에 명시했다.

### 5.2 두 종류의 429를 같은 상태 코드가 가린다

레이트리밋 429('The API rate limit has been exceeded')와 월 한도 429('You have reached your monthly limit')는 상태 코드가 같지만 대응이 정반대다. 전자는 백오프 후 재개, 후자는 재시도해도 소용없으니 발송 중단·운영 알림이다. 상태 코드만 보고 재시도하는 클라이언트는 월 한도에서 무한 재시도한다. 그래서 동등 분할로 둘을 나누고 각각 TC(RLM-001, RLM-005)를 두어 message로 분기하는지 검증한다.

### 5.3 24시간 '직후'가 가장 위험한 경계

리트라이 키는 24시간 보관되고 그 뒤 같은 키는 신규 요청이 된다. 즉 24시간 10분 뒤 재시도는 **플랫폼이 정상 동작해도 중복 발송**이다(TC-IDM-005). 이 경계는 플랫폼 결함을 찾는 게 아니라 클라이언트 재시도 창을 24시간보다 훨씬 짧게(예: 1시간) 제한해야 한다는 설계 결론을 내기 위한 케이스다. 경계값이 항상 "틀린 곳"을 찾는 건 아니고, "설계 규칙이 필요한 곳"을 찾기도 한다.

### 5.4 200이 도달을 뜻하지 않는다

차단·탈퇴·미친구 사용자에게 push는 200을 돌려준다. 결정 테이블 4행이 이 경우다. 여기서 Fail을 매기면 플랫폼 문서와 어긋난다. 대신 "200은 수락, 도달은 별도 지표"라는 해석 규칙을 클라이언트 설계에 넣고, TC-PSH-003은 '200이지만 미도달'을 **기대 결과**로 적었다.

## 6. 실행 구분을 '무발송 / 발송 / 장기·한도'로 정의한 이유

**결정** 1번 프로젝트의 비결제/실결제/장기 대신, 이 프로젝트는 무발송 / 발송 / 장기·한도로 실행 구분을 둔다.

**대안** 1번과 같은 축을 그대로 쓰기, 또는 실행 구분 없이 우선순위만 쓰기

**이유** 이 프로젝트의 비용 축은 돈이 아니라 **월 무료 메시지 한도와 가이드라인 제재**다. validate·토큰·조회·웹훅 수신은 한도를 쓰지 않아 PR마다 돌릴 수 있고(무발송 69건), 실제 발송은 테스트 계정에게만 하루 상한 안에서(발송 27건), 15분·24시간·14일·30개·60/h는 시간이나 한도가 필요하다(장기·한도 6건). 이 축이 있어야 수행 순서(0차 스모크 → 1차 무발송 전수 → 2차 발송 → 3차 장기)가 설계에서 자동으로 나오고, CI 배치(PR = 무발송, 나이틀리 = 발송 일부)도 같은 축으로 결정된다.

**결과** 요약 시트에 실행 구분별 집계가 있고, 계획서 5.1이 건수를 자동 반영한다.

## 7. 가이드라인이 금지한 것을 어떻게 테스트하는가: 모의 서버

**결정** 레이트리밋 초과·500·타임아웃·500명 수신자·월 한도 시나리오는 LINE API를 흉내 내는 **모의 서버(MK1)**에서 클라이언트 동작을 검증하고, 실플랫폼에서는 한도가 가장 낮은 webhook test(60/h)에서 1회 초과만 관찰한다.

**대안**
- 실플랫폼에 429가 나올 때까지 요청 보내기
- 한도·장애 시나리오를 범위에서 제외하기

**이유** 개발 가이드라인이 한도 초과 요청·부하 테스트·동일 사용자 대량 발송·무효 userId 요청을 명시적으로 금지한다. 어기면 채널 제재로 테스트 자체가 중단된다. 그렇다고 제외하면 "500 뒤 재시도에서 중복 발송하지 않는가", "월 한도 429에서 무한 재시도하지 않는가" 같은 **가장 비싼 결함**을 검증할 수 없다. 이 결함들은 전부 우리 쪽 클라이언트 로직에 있으므로, 플랫폼 응답을 모의하면 플랫폼 없이도 결정적으로 검증된다. 다만 모의 서버는 문서대로만 응답하므로, 문서와 실제가 다른 부분(Q08의 Retry-After 유무 등)은 실플랫폼 1회 관찰로 보정한다.

**결과** MK1 의존 TC 10건(CMN-008, MLT-002/006/010, IDM-007/008, RLM-001/003/005/006). 결함 분류에 '플랫폼 / 봇서버 / 클라이언트'를 두어 모의 서버 케이스의 Fail이 어느 쪽 책임인지 바로 드러난다.

## 8. 웹훅은 플랫폼을 거치지 않고 봇서버를 직접 호출한다

**결정** 서명 검증·중복 제거·standby·미지 이벤트 TC는 저장한 원문 웹훅 샘플(MS3)에 서명을 붙여 봇서버 B1에 직접 POST한다. 실제 플랫폼 웹훅은 샘플 확보(WHK-001)와 재전송 관찰(WHS-005)에만 쓴다.

**대안** 모든 웹훅 TC를 LINE 앱에서 메시지를 보내 유발하기

**이유** 서명 불일치·누락·특수문자 본문은 플랫폼이 만들어 주지 않는다. 직접 호출해야 만들 수 있고, 플랫폼을 거치지 않으니 결정적이고 빠르며 월 한도도 쓰지 않는다. 핵심은 **원문 바이트로 서명을 계산**하는 것이다. TC-WHK-002 3단계에서 json.loads → json.dumps로 재직렬화한 문자열로 계산하면 불일치함을 일부러 보여 준다. 이게 실무에서 가장 흔한 서명 검증 실패 원인이다.

**결과** WHK·WHS 19건 중 14건이 API 자동화로 배치됐고, 봇서버 서명 테스트는 계획서 8.3에 parametrize 예시로 남겼다.

## 9. 우선순위 기준을 '돈'에서 '중복·유실·위조'로

**결정** P1은 중복 발송·메시지 유실·위조 웹훅 처리·인증 우회로 이어질 수 있는 경로와 문서에 명시된 핵심 계약이다(37건).

**이유** 메시징 플랫폼에서 가장 비싼 결함은 사용자에게 같은 메시지가 두 번 가는 것(신뢰 손상), 보낸 줄 알았는데 안 간 것(유실), 위조 요청을 처리한 것(보안)이다. 금액 오류가 P1이던 1번 프로젝트와 기준은 다르지만 "고객에게 직접 보이는 손상"이라는 원칙은 같다. 결함 심각도 S1 정의도 같은 기준으로 맞췄다.

## 10. 의도적으로 제외한 것

| 제외 항목 | 이유 |
|---|---|
| 성능·부하 테스트 | 가이드라인이 플랫폼 경유 부하 테스트를 명시적으로 금지. 봇서버 부하는 별도 환경 과제 |
| Flex 메시지 레이아웃·리치 메뉴·오디언스 CRUD | 케이스 수는 늘지만 품질 관점이 중복. 메시지 타입은 페어와이즈 축으로만 포함 |
| LINE Login·LIFF | 별도 제품. 인증 상태 전이는 4번 프로젝트(SSO)에서 다룸 |
| 요금제 변경·추가 메시지 구매 | 비용 발생. 월 한도 초과는 모의 서버로 대체 |
| 실제 자동화 코드 구현 | `public-api-quality-lab`의 역할. 이 프로젝트는 그 입력이 되는 설계까지 |

## 11. 한계와 사내 환경이라면 달라질 것

- **계정 유형 제약**: 팔로워 ID API는 verified/premium 전용이라 개인 채널에서는 403으로 Blocked된다. 사내 인증 계정이면 PGN-001~004가 그대로 수행된다.
- **도달 확인**: 200 ≠ 도달이라 UI 구분 TC 22건은 LINE 앱·콘솔에서 사람이 확인해야 한다. 사내에 테스트 계정 수신함을 읽는 도구가 있으면 자동화된다.
- **재전송 시점**: 횟수·간격이 비공개라 WHS-005~007은 대기가 필요하다. 사내라면 플랫폼 파트너 문의로 확정 가능.
- **모의 서버의 한계**: 문서대로만 응답하므로 문서와 실제의 차이는 잡지 못한다. 실플랫폼 1회 관찰(RLM-002)로 보정하되, 사내 스테이징 채널이 있으면 한도 시나리오를 실제로 돌릴 수 있다.
- **실행과 결함**: 이 프로젝트는 설계까지다. 실행했다면 질의 13건의 확인 결과, 플랫폼/봇서버/클라이언트별 결함 분류, 수행률·Pass율이 추가된다.

## 12. 한 문장 요약과 예상 질문

### 12.1 한 문장으로

> 공개 문서가 흩어 놓은 규칙을 요구사항 22건으로 모으고, 비보장 항목은 관찰로 분리하고, 중복 발송·웹훅 위조라는 가장 비싼 결함을 결정 테이블·상태 전이·경계값으로 102건 설계한 뒤, 가이드라인이 금지한 한도·장애 시나리오는 모의 서버로 옮겨 3분의 2를 PR 단위 자동화로 내려보낸 플랫폼 API 테스트 설계안.

### 12.2 설계 하이라이트 3가지

1. **멱등성을 상태 전이로** — 리트라이 키의 200/409/24h 만료/키 누락을 8개 전이로 정리하고, "24시간 직후 재시도는 플랫폼이 정상이어도 중복"이라는 결론을 클라이언트 재시도 창 규칙으로 옮김
2. **웹훅 보안·신뢰성을 봇서버 직접 호출로** — 원문 바이트 서명 검증, 재직렬화 함정, webhookEventId 중복 제거, timestamp 순서 역전을 플랫폼 없이 결정적으로 검증
3. **가이드라인 제약을 설계로 흡수** — 금지된 한도·장애 시나리오를 모의 서버로 옮기고 실플랫폼은 1회 관찰로 보정. 두 종류의 429를 message로 분기하는지까지 검증
