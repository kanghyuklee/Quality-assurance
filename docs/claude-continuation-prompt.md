## 반드시 지킬 규칙

- 범위는 **테스트 계획서 설계 + 테스트 케이스 작성 + 설계 노트**까지. 테스트 실행, 실결제, 결함 리포트 작성은 하지 않는다. 결제가 필요한 케이스는 "실행 구분: 실결제"로 태깅만 하고 "수행 시 절차"로 기술한다.
- 요구사항은 지어내지 않는다. 공개 명세·정책·문서에서 역도출하고 각 항목에 출처를 남긴다. 확정 불가한 동작은 질의사항(Q01~)으로 분리하고 "현재 동작 기록 후 판정" 원칙을 적는다.
- 설계 근거는 요구사항 / 리스크 기반 / 추가 검증으로 태깅. 우선순위 P1~P3. 자동화 구분 API / UI / 수동. 실행 구분은 프로젝트 성격에 맞게 정의한다.
- 설계 기법은 이름만 나열하지 말고 "어떤 규칙에 왜 그 기법이 맞는지"를 표로 쓴다(결정 테이블·경계값 3점·상태 전이·동등 분할·페어와이즈·오류 추정).
- 계획서는 Markdown(PDF 아님), 케이스는 xlsx(openpyxl, 수식은 COUNTIF/COUNTIFS/SUM/IF만, 요약 시트 자동 집계, 입력 칸 노란색 FFF2CC, 헤더 674EA7). LibreOffice가 없으니 수식은 스크립트에서 범위·참조를 자체 검증하고 `wb.calculation.fullCalcOnLoad = True`를 켠다.
- 파일명은 `<서비스>_<플랫폼>_<기능>_테스트계획서.md` / `_테스트케이스.xlsx` / `_설계노트.md`. 폴더명은 영문 kebab-case로 `projects/` 아래.
- 과거 사전과제(마키나락스 Runway SSO)의 제품명·요구사항 원문은 어떤 산출물에도 넣지 않는다.
- 문서는 한국어. 루트 `README.md`의 프로젝트 표에 새 프로젝트 행을 추가한다.
- 커밋은 `feat(<project>): ...` / `docs(<project>): ...` 형식, main에 바로 push.

## 작업 방식

- 시작할 때 "어느 프로젝트부터 할지"만 확인하고, 그 뒤엔 공개 문서 조사 → 요구사항·질의 정리 → TC 설계 → 빌드 스크립트 → 계획서·케이스 생성 → 설계 노트 → README 갱신 → 커밋/push 순으로 진행한다.
- 선택지를 묻기 전에 추천안을 먼저 제시한다. 질문은 꼭 필요한 결정에만.
- 설계 중 내린 판단과 이유를 설계 노트에 결정 → 대안 → 이유 → 결과 형식으로 남긴다.
